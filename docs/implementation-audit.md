# 当前实现核查

核查日期：2026-08-14

## 1. 基线判断

当前实现应以 `预约管理需求-汇总材料 - 260721.xlsx` 的 `需求` TAB 为功能基线，`预约/` 仅作为页面拆分、字段布局和交互参考。若两者冲突，以 `需求` TAB 为准。

上一版 MVP 的主要问题不是规则完全缺失，而是用户端首页和子页面体验割裂，且规则说明挤占了核心操作的视觉优先级。本轮调整统一了用户端 Material 风格，把规则收敛为低优先级折叠说明，同时保留提交时的强校验和明确错误反馈。

## 3. 规则如何在页面体现

| 规则 | UI 表达方式 |
|---|---|
| 本周只能预约下周 | 用户首页只展示下周已审核开放号段；规则放入页面底部折叠说明 |
| 取消只能预约前一天 | 我的预约卡片显示“可取消”或禁用原因，取消失败会提示规则原因 |
| 取消/最终未到进入考核 | 我的预约页展示操作记录；原号段未到仍可调整，当日最终未到才累计过号 |
| 超阈值禁约 | 用户首页展示当前预约资格；提交预约前拦截 |
| 临时预约需先审号段 | 临时预约页只展示已通过临时号段 |

规则不作为首页主信息。用户正常操作时由系统自动筛选和校验；只有查看说明、触发限制或提交失败时，才提高规则提示的视觉优先级。

## 4. 当前仍不应误认为已完成的部分

1. 这仍是静态前端 + mock API，不是生产系统。
2. 导入、权限、消息、定时任务、统计口径都需要后端和平台能力承接。
3. “每日 00:00 自动闭环”当前是按钮触发的模拟任务，真实系统需要后端定时任务、事务和幂等日志；自动闭环结果必须是未到现场。
4. “前一天取消”目前采用自然日口径：预约日期前一日 00:00-23:59:59 允许取消。如果业务要精确到小时，需要产品确认并改规则。
5. 当前 UI 参考了用户提供的低饱和卡片风格，但没有复刻参考图的业务标题和字段，因为功能仍以预约管理需求 TAB 为准。
